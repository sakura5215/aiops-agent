# 真实故障复盘：create_time 缺索引，午间活动打满连接池

> 来源：建站侠《系统性故障排查心法：从日志、链路追踪到根因定位的实战指南》
> 链接：http://www.bryh.cn/news/114970

## 现象
- 每天中午 12 点左右，应用开始大量报错「Cannot get connection from datasource」
- 持续约 20 分钟后自动恢复（典型的周期性故障）

## 排查过程
1. 时间点关联：中午 12 点联想到定时任务或流量高峰。
2. 监控验证：HikariCP JMX 指标显示报错期间活跃连接数达最大值（如 100），且很多连接「活跃」状态持续数分钟——极不正常，正常业务 SQL 应毫秒级完成。
3. 链路追踪：抓取慢请求 TraceID，发现大量时间卡在「查询用户订单汇总」这条 SQL 上。
4. 数据库侧：慢查询日志显示该 SQL 在 12 点前后执行时间从平时 50ms 暴增到 10s+，EXPLAIN 发现全表扫描，`create_time` 字段缺索引。
5. 流量分析：该「订单汇总」查询本是后台管理功能，但 API 被错误配置到了面向用户的活动页；每天中午 12 点有限时抢购活动，大量用户涌入触发未优化查询，瞬间打满连接池。

## 根因
后台管理功能的批量查询 API 被误配置到用户活动页，`create_time` 缺索引导致全表扫描，午间活动流量涌入瞬间打满连接池。

## 解决方案
- 立即：给 `create_time` 加索引，查询恢复毫秒级
- 长期：管理功能 API 与用户前端 API 路由隔离；批量查询功能使用独立、容量较小的连接池，避免影响核心交易链路

## 复盘启示
- 周期性故障（每天固定时间）优先关联定时任务或流量高峰
- 连接池耗尽通常是结果而非原因，根因往往是慢查询、事务未提交、网络分区
- 监控连接池的活跃连接数、空闲连接数、等待线程数至关重要
- 管理/批量类查询要隔离，避免拖垮核心链路
