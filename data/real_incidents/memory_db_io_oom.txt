# 真实故障复盘：磁盘 I/O 瓶颈连锁引发数据库 OOM

> 来源：达梦社区《记某个大型国企客户数据库 OOM 实战》
> 链接：https://eco.dameng.com/community/article/fd029839ebf51b5c7349262c68b3163f

## 现象
- 主库发生故障，备库接管后 17:07:03 至 17:07:51，系统分配了 8000+ 个新的数据库会话连接
- 每个连接约占用 5MB 内存，8000 个连接消耗约 40GB 内存
- 物理内存（128G）被迅速耗尽，触发操作系统 OOM，dmserver 进程被强制杀死，数据库服务彻底中断

## 根因（全链路）
磁盘 I/O 性能不足（3.8-5.7MB/s）→ SQL 执行慢发生阻塞 → 应用持续申请新连接会话 → 内存耗尽触发 OOM → 数据库进程被杀死、服务中断。

## 解决方案
1. 扩容内存至 256GB，为业务高峰期内存增长预留冗余
2. 更换更高性能 SSD，确保写入吞吐量稳定在 150MB/s 以上
3. 从根源切断「I/O 瓶颈 → SQL 超时 → 连接积压 → 触发 OOM」的故障链路

## 复盘启示
- 数据库 OOM 的表面是内存耗尽，真正的根源可能在磁盘 I/O——要看全链路而非单点
- 连接数失控（雪崩式连接增长）是 OOM 的前兆，要监控会话连接数并设上限
- 主备切换后是风险窗口，切换瞬间的连接洪峰要提前评估
