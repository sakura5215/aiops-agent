# 真实故障复盘：Druid SQL 缓存泄漏 + SQL 拼接导致 OOM

> 来源：阿里云开发者社区《一次 OOM 线上排查实录》
> 链接：https://developer.aliyun.com/article/1734721

## 现象
- 线上老项目内存使用率持续飙高，触发 OOM 报警，应用直接抛 OOM 错误，服务崩溃
- 堆 Dump 用 JProfiler 分析：大量 `com.alibaba.druid.proxy.jdbc` 相关对象堆积
- 堆中最大单个对象是 char[]，超过 500MB，存储的是项目执行的 SQL 字符串

## 根因（两个问题叠加）
1. 业务代码：单条 INSERT 通过循环拼接 SQL 字符串一次性插入大量数据，拼接后的 SQL 字符串巨大，生成的 char[] 对象占用几百 MB，被线程栈引用短时间无法回收。
2. 框架层：Druid 1.1.22 的 SQL 统计功能会无限制缓存所有执行过的 SQL 字符串（sqlStatMap），无法自动清理，拼接出的海量不同 SQL 被全部缓存，随着运行时间增长内存只涨不跌，最终撑爆堆。

## 解决方案
- 业务侧：改批量插入，避免循环拼接超大 SQL
- 框架侧：优化 Druid 配置，关闭或限制 SQL 统计缓存
- 升级 Druid 版本修复 SQL 缓存泄漏

## 复盘启示
- OOM 排查第一动作是拉堆 Dump 看「最大的对象是谁」，再顺着对象引用定位业务代码
- 内存泄漏往往不是单一原因，是「业务写法不当 + 框架已知缺陷」叠加
- 关注依赖库的已知 bug 版本（Druid 1.1.22 的 SQL 缓存泄漏是经典案例）
